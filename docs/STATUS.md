# The `pocp` status

POCP reports its result on a pull request as one commit status, **`pocp`**, on the pull request's head:

| `pocp` | Means | What clears it |
|---|---|---|
| ✅ success | verified: the required checks passed on this exact code | nothing; it's done |
| 🟡 pending: waiting for approval | only approvals are missing (a test change, a policy loosening, protected files, a CI change) | the status says why in a few words and, when it fits, the one command that adds every label (`Waiting for approval (tests edited). Run: gh pr edit N -R owner/repo --add-label pocp-approve-tests`); the reporter's comment on the pull request says why in full, with the files and lines to look at |
| 🟡 pending: inconclusive | a check didn't finish: it timed out, was killed or didn't start | re-run the job; or fix the hang or the time limit; or, for a test change, a maintainer adds `pocp-approve-inconclusive` |
| 🟡 pending: waiting for approval, CI changed | the pull request changes a CI file, so its own run can't be trusted until a maintainer adds `pocp-approve-workflow` | the same one command: it lists `pocp-approve-workflow` together with every label the run asked for, so nothing turns up one at a time |
| 🟡 pending: waiting for verify | no finished run for this pull request, its base and its head yet, or a newer run or re-run is still going | wait; after the base branch moves, re-run |
| 🟡 pending: data incomplete | GitHub's answers about the pull request were incomplete or didn't add up (for example, more files than GitHub lists, or an API error) | re-run the reporter; split a very large pull request |
| 🟡 pending: shared head | another open pull request has the same head commit | close all but one |
| ❌ failure | a required check failed, behavior changed without approval, proof is missing, or anything unexpected | fix the code in a new commit |

A pending status blocks merging just like a failure, once `pocp` is a required check. Only success allows a merge.

In local mode (`pocp init --local` or `pocp ci off`, [QUICKSTART](QUICKSTART.md#no-ci-local-mode)) POCP's workflows don't run, so there is no `pocp` status, and nothing blocks a merge.

## Why it's waiting: one comment

When the status waits for approvals, the trusted reporter also keeps **one comment** on the pull request, from the same decision:

- **why**, in a plain sentence per label, from the same function (`src/hold.js`) that `pocp fix`, `pocp gate`, the hooks and `pocp approvals` use. For a test edit it says what the test guard found, so the serious case never reads like the review-only one: "the old tests fail on the new code, so the code now behaves differently" versus "the old tests still pass on the new code, but POCP can't show on its own that the edited tests check as much as before". When the verdict isn't known to the reporter (below), it says so and points at the verify run instead of implying a pass;
- **which files and lines to look at**, each linked to the pull request's diff;
- **what the label approves** ("I accept this change in what the code does, or in what its tests check"), and that it doesn't mean "I reviewed the code";
- **the one command** that adds every label.

It is updated in place, never posted again: on each run the reporter finds its comment by a hidden marker and edits it only when the text changed. Anyone can type the marker, so only a comment by the reporter's own identity counts (the app it posts as, `performed_via_github_app`, else its login); any extra marker comment by that identity (two reporters racing, or one another workflow posted as the same identity) is deleted, and the oldest is rewritten. Once the status is green it says so ("approved, nothing waiting") rather than disappearing; while the status still waits for a person without naming labels (an approval to apply again, a check that didn't finish) it says it is still waiting, with the status's text. No comment is posted for a pull request that never waited, and a comment that would pass GitHub's size limit drops the line links, then the file list, first.

**Where the verdict comes from.** It is typed all the way, never read from text a pull request could have written: verify takes it from the test guard's result (`behavior-changed`, `detection-dropped`, `baseline-red` or `needs-review`) and writes the gravest one into the same isolated approval file as the labels (`verdict=…` after the labels line). The `mark` step accepts only those four exact words, and one of four steps, `verdict-behavior-changed` and so on, runs after `approvable`. The reporter believes a verdict step only when `approvable` ran and exactly one verdict step did; otherwise (checks not isolated, a wait for more than test approvals, a workflow older than 1.5, or an unapproved CI change) it names no verdict. The verdict only chooses words: it never changes a state.

The status line has room for little: it says why in a few fixed words and the command, within GitHub's 140 characters (`Waiting for approval (tests edited). Run: gh pr edit …`). With a verdict the words say it: `(old tests FAIL on new code)`, `(tests edited, old tests pass)`; without one, `(tests edited, verdict unknown)`. When both don't fit it uses one word per label (`(tests FAIL, CI)`); then the command alone; then the words and the labels; then the labels alone. For old tests that fail or tests that catch less, the words and labels come before the command alone, so "FAIL" is never the part that's dropped.

**Only the reporter writes it.** The comment is posted by `pocp status-report` in the privileged `pocp-status.yml`, from the default branch's code, never by anything the pull request runs. It says only what the reporter knows itself: the labels it decided the status waits for, GitHub's own list of the pull request's files and their changed line ranges (read from the hunk headers only), and the default branch's config, which decides which files each label covers. No text a run printed is relayed. File names are the pull request's own, so each is shown only inside a code span with its control, bidi and zero-width characters replaced: a name can't add a line, markdown, a link or image, an @mention, an issue reference or a hidden comment. A comment that fails to post never changes or fails the status.

**Permissions:** none new. The comment is posted with the token the reporter already uses to remove stale labels (`LABELS_TOKEN`, the status action's `labels-token`: `github.token` with `pull-requests: write`, which `pocp-status.yml` already grants), so it appears as `github-actions[bot]`. With `labels-token` empty, no comment is posted; with any other token (a personal token, another App), the reporter takes its comment back and posts none, since it couldn't recognise it next time. What that identity doesn't settle: any workflow in the repository with a write token also posts as `github-actions[bot]`, so a same-repository branch's workflow could post a misleading comment that looks like POCP's (without the marker, or with it until the reporter's next run deletes it), or edit the reporter's own comment until its next run rewrites it. That holds with the reporter's own App too: the comment still posts with `github.token`. The `pocp` status is the record; the comment explains it. Posting the comment as the reporter's own GitHub App would close this, and needs the App to have pull-request write permission. The verify run still has every detail; the comment's "what POCP found, in full" links to it.

**Opting out:** set `"ci": { "pr_comment": false }` in the default branch's `.proof/config.json`. The status keeps its short reason.

## Approvals

Each label covers one thing, only on the head it was added to. A label counts only if someone with write access added it after this head's first verify run, and after the pull request's latest force-push (or it carries over through "Update branch", or sticks to what was approved, below). verify checks this itself (`label-freshness: github` in `pocp.yml`), and so does the reporter, both from GitHub's API. A label left on from before a push doesn't count: verify says "pocp-approve-tests was added before this commit: review the new commits and re-apply it", and the reporter removes it, so adding it again is the approval.

### No `pull_request_target` (since 1.3.1)

From December 2, 2026, GitHub blocks `pull_request_target` workflows by default in public repositories that have no Actions event policy ([GitHub's docs](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)). POCP's workflows don't use it, so there is nothing to allow in the repository's settings. `pocp.yml` runs on `pull_request` with read-only permissions, and its token goes only to verify's own process, never to a check it runs. `pocp-status.yml` runs on `workflow_run`. Up to 1.3.0, `pocp-labels.yml` removed approval labels on push, on `pull_request_target`: `pocp doctor` flags it, and a `pocp.yml` without `label-freshness`, and `pocp init --github --force` regenerates the workflows and removes it. An old `pocp.yml` still works as it did, with a warning on each run that passes an approval.

A pull request whose `pocp.yml` run never starts (a first-time contributor's fork, waiting for a maintainer to approve the run) gets no `pocp` status until it runs, so it can't merge.

**Several approvals at once:** `pocp approve owner/repo#12` (also `pocp approvals --approve`) shows every approval the pull request waits for, with the diff each covers, and adds all of them after you type the pull request's number once. Your answer covers exactly what was listed: each label is still checked on its own, and anything verify reports later needs its own approval. It must be run by a person at a terminal. `pocp-approve-workflow` isn't included: add it yourself after reviewing the CI change. When verify waits for a label, its "what to do" (and the job summary, and `next_steps` in `verify --json`) marks that step `[maintainer, not the author]` and names the pull request and this command; it is never the author's or an agent's step.

**Updating the branch keeps the approval.** If the push is only a merge of the base branch into the approved head (GitHub's "Update branch"), `pocp-approve-policy` and `pocp-approve-coverage` still count for the new head, in verify and in the reporter, only if all of these hold:

- the new head's parents are the approved head and the pull request's current base;
- the label was last added by someone with write access, after the approved head's first run for this pull request;
- the merge changed no file the pull request changes, and no policy file under `.proof/` (proof records in `.proof/packets/`, which nearly every merged pull request adds, don't count; the pull request's own packets are covered by the rule before);
- after the merge, the pull request changes only files the approved head already changed (so a merge that keeps an old version of a file the base changed doesn't carry);
- since the approved head branched off, the base branch changed no policy file under `.proof/` (again, proof records don't count) and none of the files the approval covers;
- GitHub's file lists for the merge are complete.

Otherwise the status says to approve again: remove the label and add it back. `pocp approve owner/repo#N` reads that status and does it for you (after you confirm), even when verify itself passed with the label on. The approval is kept, never the result: the merged head is verified again on the new base and turns green only from its own run. On its own, this rule carries over one merge only, and refuses a merge whenever the base touched a file the pull request changes. Sticky approvals (below) cover the rest. Inconclusive and workflow approvals never carry over. Since 1.5, `pocp-approve-tests` doesn't carry this way either: it may accept a behaviour change, decided on the run that showed it, so it reaches a new head only as a review-only hold, through sticky approvals.

**Approvals stick to what was approved (since 1.5).** With "require branches to be up to date", every merge to the base made every other open pull request update, and each update voided its approvals. Now `pocp-approve-tests` and `pocp-approve-policy` are bound to the pull request's own changes at the head they were given for, not to that head's sha. A later head keeps the approval, through any number of updates, when all of these hold:

- the label was last added by someone with write access, and is still on (removing it revokes the approval; adding it again binds it to the head at that moment);
- the approved head is the pull request's head when the label was last added: the head of its newest `pocp.yml` run created before then, which must also be the head of the run the label's own event started, with no force-push in between (so a head pushed seconds before the label, before its run existed, never lets the label bind to the older head);
- the new head is exactly the approved head plus base content: its tree is the clean merge of the approved head with the base commit the new head contains (`git merge-tree`, with `.gitattributes` merge drivers off). A conflict resolved by hand, a merge that keeps the pull request's side of a file the base changed, or any edit of its own (a line, a mode, line endings, a rename, a binary, a submodule) voids it. verify decides this with git, before any of the pull request's code runs;
- the approved head changed no CI file, and the base's policy files under `.proof/` are the same as when the approved head's run was judged;
- for `pocp-approve-tests`: the hold is review-only on both heads (the test guard's verdict is `needs-review`: the old tests still pass on the new code, as the `verdict-needs-review` step records it). A hold whose old tests fail on the new code (`behavior-changed`), whose edited tests catch less (`detection-dropped`) or whose old tests already failed (`baseline-red`) never carries over: the label is removed, and adding it again re-runs verify on the new head;
- for `pocp-approve-tests`: the same files are held as test changes as at the approved head. A base update that makes another file count as a test (a new glob, a test that now imports a helper, a newer verifier) voids it.

What verify found travels as steps of the verify job: `pocp-held tests <fingerprint>` (the set of files held as test changes) and `pocp-approval <label> <verdict> <approved head>` (`same`, or why not: `content`, `conflict`, `ci`, `policy`, `gone`). Like the `approvable` step, verify writes them to a file in the runner's temp folder that isolated checks can't reach (`--record-file`), and a step that prints nothing of the pull request's reads it, checking each line against a fixed pattern. The reporter trusts them only from a head that changes no CI file, and the approved head's only when it changed none either. When verify finds the pull request's own changes differ, its log names the files, the label doesn't count, and the reporter removes it, saying why. While the new head's run is still going, or GitHub's lists are cut short, the label is refused but stays on. Once that run has finished, what it couldn't settle (verify couldn't compare, for example a git without `merge-tree --write-tree`, or the approved head's run left no usable record) is judged as before: the label is removed, and adding it again approves the new head. The approved head force-pushed away is `gone`. `gone` is also why a rebase ("Update branch" with rebase, or a force-push) usually needs a new approval on GitHub: CI fetches the pull request's branches, and the approved head is no longer on one.

A pull request approved before this (its approved head's run has no records) needs one more re-label. A `pocp.yml` without the record steps judges labels as before, except that a test approval no longer carries over a merge of the base (above). Sticky test approvals turn green from the waiting run, as above; a sticky policy approval is applied by verify itself, and the reporter checks the same records. `pocp-approve-coverage`, `-inconclusive` and `-workflow` stay bound to their head (the workflow label because the run that would record it is the pull request's own workflow). Local mode follows the same rule: `--accept-test-change=<sha>` (or `--accept-policy-change=<sha>`) given for the branch head also covers a later head that is exactly that head plus base content: a merge into the base (fast-forward or not), or a merge that brings in base-only changes. For a test approval, verify checks after its checks that the hold is review-only and holds the same test files; otherwise it waits for an approval of the new head and says why. A merge whose resolution edits a file is a change of its own: verify names the files, and the approval doesn't cover it.

| Label | Covers |
|---|---|
| `pocp-approve-tests` | a change to existing tests or test setup whose check ran to the end |
| `pocp-approve-policy` | loosening `.proof/` rules, signers or CI files |
| `pocp-approve-coverage` | commits listed in `.proof/exceptions.json` that have no proof |
| `pocp-approve-inconclusive` | a test change whose check **didn't finish**. A test approval doesn't cover this: the person approving the test change hasn't seen whether the code hangs. |
| `pocp-approve-workflow` | a change to a CI file, which makes the pull request's own run untrustworthy. It counts only if added after the head's first run by someone with write access who **isn't the pull request's author** (see below). It approves the workflow change only: the run is then judged like any other, so anything else it waits for still needs its own approval. |

A plain re-run that didn't finish is never cleared by a label, only by a re-run that finishes, or a fix.

**A test approval turns the status green without running verify again** (with `POCP_STATUS_LIVE` on and isolated checks, the default with `isolate: true`). When verify waits for `pocp-approve-tests` only (with `pocp-approve-workflow` too, when CI files changed), it writes that to a file in the runner's temp folder, which the isolated checks can't reach, and a step that prints nothing of the pull request's turns it into the run's `approvable` and `needs-tests` steps (docs/THREAT-MODEL.md). Once the label, and any the run already relied on, is on the pull request, added by a writer after this head's first run, the reporter sets success from that run. The label accepts exactly the test-change findings that run listed, so a re-run with it would find the same checks passing. On the label event, the verify job's first steps ask whether that is now the case (`pocp status-report --predict-approval`, with the reporter's own code and config: the default branch, or the status action at the same ref as `pocp-status.yml`, else no skip); if so, the rest of the job is skipped (the run shows `approved-without-run`, and the reporter sets it aside like a skipped run), and the status turns green without a full verify. It is also skipped when the pull request has moved past the labelled head, whose own run decides. The prediction is part of the verify job, so label runs keep the order their events came in; it only decides whether verify runs, and the reporter decides the status. Only a review-only wait goes green this way (since 1.5): the run's `verdict-needs-review` step says the old tests still pass on the new code, so the person only had to read the edit. A behaviour change (`behavior-changed`, `detection-dropped`, `baseline-red`), a run whose verdict this reporter can't read (an older `pocp.yml`), a policy or inconclusive approval, a run that wasn't isolated, `--ci-results`, the variable off, or any doubt: the label re-runs verify, which applies it, since a policy approval changes which rules judge the run, an inconclusive one is for a check that didn't finish, and a behaviour change is decided on the run that shows it.

### Who can approve a workflow change

By default (`"ci": { "workflow_approver": "independent" }`), `pocp-approve-workflow` must come from a writer other than the pull request's author. On a team, that means a second person reviews any change to CI.

A solo maintainer can set `"workflow_approver": "any-writer"` in the base branch's `.proof/config.json`. That's a policy loosening, so it needs `pocp-approve-policy`. Be clear about what it means: **GitHub sees an agent using your token as you.** So with `any-writer`, the author can approve their own workflow change, and so can a coding agent working with the author's token. Its own CI change then turns green on the label it added itself. Choose it only when no second person exists to review CI changes. `independent` stays the default for every other project.

POCP's own repository uses `any-writer`, because it has one maintainer.

The same holds for every approval label. A label shows that an account with write access added it; it can't show that a different person was involved. For approvals from someone other than the author on every change, also require pull request reviews from code owners in branch protection.

## How it's decided

Two workflows:

- **`pocp.yml`** runs `verify` on the pull request, as before. Its first step, `pocp-run pr-<number> base-<base sha>`, names the pull request and base the run evaluated. It records verify's result in which step runs: exactly one of `verified`, `waiting`, `inconclusive` or `failed`, plus an `approval-*` step for each approval passed to verify, a `needs-*` step for each label it waits for, and `approvable` when it waits for `pocp-approve-tests` only and the checks were isolated, or `approved-without-run` when its prediction found verify needn't run. `verified` runs only when the verify step itself exited 0, which GitHub takes from the process's exit status. The step's `code` output, which picks between `waiting`, `inconclusive` and `failed`, is weaker, and never makes a run green. With `--isolate` (the example workflow's default, and POCP's own workflow once its base verifier supports it), the checks verify runs, which are the pull request's code, run as separate unprivileged users: they can't write the file GitHub reads outputs from, change the verifier, read the job's tokens or signal verify, and if that isolation can't be set up the run is red. Without `--isolate`, they run as the job's own user and could write that file, so the most a forged output can do is turn a failure into a wait (yellow) or the reverse. docs/THREAT-MODEL.md ("Pull-request code in the verifying job") says exactly what the isolation covers and what it doesn't: the network, the kernel, memory and disk, and anything that ran before verify in the job.
- **`pocp-status.yml`** is the trusted reporter. It runs from the default branch, on `workflow_run`, and never checks out or runs anything from a pull request. On every event it recomputes from GitHub's API:
  1. Which open pull request has this head, and whether it's still the head. If not, nothing is written.
  2. **Whether the data is complete.** Every list it reads (open pull requests, the pull request's files, runs, jobs) must be read to the end, and the file list must match the pull request's changed-file count and stay under GitHub's 3000-file limit. Anything cut short, missing or inconsistent, or an API error or rate limit, is pending, whatever labels are on.
  3. **Whether the head is shared.** A commit status belongs to the commit, so every pull request with that head shows it. If more than one open pull request has this head, the status stays pending.
  4. **Whether the run can be trusted.** On GitHub, a pull request runs its own copy of `pocp.yml`, so a pull request that edits a CI file could make its run report anything. If the diff touches any CI file (`ci.files` in the base's `.proof/config.json`, with the defaults always included), the run's steps are ignored and the status stays pending until `pocp-approve-workflow`.
  5. Only runs of the trusted workflow (by id and path), for this repository's `pull_request` event on this head, whose `pocp-run` step names this pull request and its current base. A run or re-run attempt still queued or running means pending. Otherwise the newest finished one decides, so the order things finish in doesn't matter; if that one was cancelled, it's pending. Runs that say nothing are set aside: a skipped run, and a run cancelled before its verify job ran any POCP step (adding several approval labels at once starts a run per label, and all but one are cancelled while queued). A run cancelled after its marker or verify step started still counts, so it holds an older success at pending.
  6. If that run relied on an approval, the label must still be on the pull request now, and it must have been applied last by someone with write access, after this head's first run and after the pull request's latest force-push (GitHub lets roles without write access manage labels; a force-push can bring back a head that ran before the label was given for another). The same holds for `pocp-approve-workflow`, which also has to come from someone other than the author.
  7. A run that waits for `pocp-approve-tests` (and nothing but the workflow label) with an `approvable` step is green when that label, and every label the run relied on, passes rule 6. Anything else stays pending, naming the labels. A run with `approved-without-run` (its prediction skipped verify) is set aside, like a skipped run.
  8. The run must have every step this reporter reads (`verified`, `waiting`, `inconclusive`, `failed`). A run from an older `pocp.yml` stays pending with "update pocp.yml", never green. A newer run that doesn't name a pull request and base (it stopped before its first step, or comes from an older workflow) holds the status at pending: an older green is never revived past it.
  9. Right before writing, it reads the pull request again. If the head moved, it writes nothing for the old head. If the base, the labels, or the set of open pull requests on that head changed, it writes pending instead, so an older green can't stand on evidence that is no longer current; the event that changed it runs the reporter again. Retargeting a pull request (`edited`) re-runs verify and the reporter.
  10. After writing, it removes each approval label GitHub's data shows doesn't count for this head (added before its first run, before a force-push, or by someone without write access), with `github.token` (`pull-requests: write` on that job only), so the pull request shows it needs approving again. A label the data can't settle (an API error, a list cut short) is left on, and refused. The removal starts no new run: the status just written already refuses the label.

If your `pocp.yml` was written before the `pocp-run` step existed, add it (`pocp init --github --force` rewrites the example): without it no run counts, and the status stays pending.

The status text is built from fixed words only: nothing a pull request writes reaches it. A waiting run's `needs-tests`, `needs-policy` and `needs-inconclusive` steps (from verify's `needs` output, since 1.4) pick which of the fixed label names it lists, with the pull request's number and repository, as `Waiting for approval. Run: gh pr edit N -R owner/repo --add-label …` (or the labels alone when the command doesn't fit GitHub's 140 characters). Those steps choose text only: the state comes from the rules above, and a pull request that lists the wrong labels only names the wrong labels on a status that stays pending. A `pocp.yml` without them gets the generic "Waiting for a maintainer's approval" text. What each label approves, in plain words, is in the run's summary, which the status links to. That summary ends with one line, `Checked by POCP · how this works`, linking to [HOW-IT-WORKS.md](HOW-IT-WORKS.md); the status text itself never carries it.

## Give the reporter its own identity

GitHub matches a required check by its name and the app that set it. By default the reporter and every workflow in the repository post as the same app, GitHub Actions. A pull request from a **fork** gets a read-only token and can't post a status. But a branch pushed to **this** repository by someone with write access (including an agent using a maintainer's token) can edit a workflow to give itself `statuses: write` and post its own `pocp: success`, and branch protection can't tell it from the reporter's.

Close that by giving the reporter its own GitHub App and requiring `pocp` from that app only. You need this when an agent pushes branches with your token. It needs a public repository, or GitHub Pro or Team for a private one: on GitHub Free, environment secrets and deployment branch rules work only in public repositories, and without them the app protects nothing (see "Why the environment matters" below).

1. **Create a GitHub App** (Settings → Developer settings → GitHub Apps → New). No webhook. Repository permissions: Commit statuses *read and write*; Actions, Contents, Issues, Pull requests *read*. Install it on the repository. Generate a **private key**. The app's settings page (General → About) shows two IDs: the **App ID**, a number, and the **Client ID**, which starts with `Iv`. Each goes in a different place below.
2. **Create the environment `pocp-reporter`** (repository Settings → Environments). Under *Deployment branches and tags*, choose *Selected branches and tags* and add only your default branch. Add the secret `POCP_REPORTER_KEY` (the whole private key file) and the variable `POCP_REPORTER_CLIENT_ID` (the **Client ID**) to the environment.
3. **Pin the required check to the app.** Set `ci.reporter_app_id` in `.proof/config.json` to the **App ID** (the number) and run `pocp ci required --apply`: it requires `pocp` from that app only and leaves other checks as they are. (By hand: in branch protection, set the required `pocp` check's source to the new app instead of "any source".) `pocp ci required --check` and `pocp doctor` report a required `pocp` check that isn't pinned to it, or, without `ci.reporter_app_id`, one that any source or GitHub Actions can post. Changing or removing `ci.reporter_app_id` later is a policy loosening.

The example `pocp-status.yml` already runs in that environment and uses the app when `POCP_REPORTER_CLIENT_ID` is set; without it, it posts as GitHub Actions as before.

Why the environment matters: secrets in an environment limited to the default branch reach only jobs running from the default branch. The reporter runs from there (`workflow_run`). A pull request's own workflows run from its branch or merge ref, so a branch that edits a workflow can't read the key, can't post as the app, and anything it posts as GitHub Actions doesn't count. Keeping the key in a plain repository secret would let any workflow on any branch read it, and the app would protect nothing.

What it doesn't cover: anyone who can change the repository's settings. An **admin** can loosen the environment's branch rule, the branch protection or the app, so a coding agent holding an admin token (a classic token with `repo` scope on a repository you own is one) can undo all of this. Give agents a fine-grained token without the *Administration* permission. Until the app is set up, read the diff of any same-repository pull request that touches CI files before merging.

## Turning it on

Two settings decide whether a wait is yellow or red, and they must change together:

1. the repository variable `POCP_STATUS_LIVE` set to `true`. Waits then pass the `verify` job (no red, no failure email), and label events other than `pocp-approve-*` are ignored;
2. branch protection requiring `pocp`, not `verify`.

With the variable on and `verify` still required, a waiting pull request would show a passing `verify`, and an ignored label event makes a skipped `verify` check, which GitHub counts as passing. POCP never sets the variable while `verify` is required.

- `pocp init --github`, on a GitHub repository, sets the variable through your `gh` login (`--no-live` skips it). A new project requires nothing yet, so this is safe, and its first waiting pull request is yellow.
- `pocp ci required --apply`, with `pocp` in `ci.required_checks` (what `init --github` writes), changes branch protection first, requiring `pocp` and dropping `verify`, then sets the variable. It requires `pocp` only once `pocp-status.yml` is on the protected branch; before that nothing would post the status and every pull request would be blocked.
- On a free plan's private repository GitHub has no branch protection: the variable is set and the status shows, but nothing blocks a merge.

To roll back, unset the variable and require `verify` again.
